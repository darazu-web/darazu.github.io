## テーブル構成

```
設備種別 ─┐
場所 ─────┼─→ 設備 ←─── 稼働ログ ───→ 使用者
部署 ─────┘     ↑                        ↑
                └──── 貸出 ──→ 貸出先 ───┘
```

| テーブル | 所有 | 代替キー | 役割 |
|---|---|---|---|
| 設備種別 | 組織 | 種別コード | メンテ周期・稼働可能時間の既定値 |
| 場所 | 組織 | 場所コード | **短縮番号の番号帯を持つ** |
| 部署 | 組織 | 部署コード | 自己参照で階層を持てる |
| 貸出先 | 組織 | 貸出先コード | 社外貸出の相手 |
| 使用者 | 組織 | 社員番号 / UPN | **UPN が Entra との突合キー** |
| 設備 | ユーザー | 設備コード / 短縮番号 | **現在の状態を持つ唯一の場所** |
| 稼働ログ | ユーザー | なし | 分析の元データ |
| 貸出 | ユーザー | なし | 貸出1件分 |

### なぜ設備に「現在の状態」を持たせるのか

稼働ログを毎回集計すれば現在の状態は求まりますが、ホーム画面のギャラリーで
設備1件ごとに集計をかけると委任されず、2000件で頭打ちになります。
**設備側に非正規化して持つ**ことで、一覧表示が単純な Filter だけで済みます。

その代わり、設備の状態とログの実体がずれる可能性が生まれます。
これを毎朝直すのが **フェーズ5-3 の整合性チェック**です。セットで考えてください。

## 1-7 代替キーを先に作る理由

| キー | 効いてくる場面 |
|---|---|
| 短縮番号 | テンキー入力の `LookUp` が委任される。ここが遅いとアプリ全体が使い物にならない |
| 設備コード | CSV の再投入が upsert になる（台帳を直して流し直すだけで済む） |
| 社員番号 | 使用者マスタの再投入が upsert になる |

代替キーはインデックス作成が非同期です。作成直後は `Pending` 状態で、
数分〜10分ほどで `Active` になります。スクリプトはこれを待ってから終了します。

## 1-8 セキュリティロールを後回しにしない

**全テーブルが揃ってから権限を設計すると、どのロールにどの権限を与えたか追えなくなります。**
このリポジトリでは権限を `schema/security.json` に**データとして**持っているので、
テーブル作成直後にそのまま流せます。

| ロール | 対象 | 要点 |
|---|---|---|
| 設備-使用者 | 現場 | 設備に **Write が必要**（使用開始でステータスを更新するため）。Delete は与えない |
| 設備-管理者 | 保全部など | 全テーブルの CRUD＋割り当て・共有 |
| 設備-システム | サービスアカウント | フロー実行用。人には割り当てない |

`Deploy-Security.ps1` は **JSON の内容でロールの権限を上書き**します。
ポータルで手で足した権限は、次回実行時に消えます。権限を変えたいときは JSON を直してください。
（これは意図した動作です。「誰かが手で足した権限」が残り続けるほうが危険です）

### 使用者に設備の Write を与えることについて

現場の使用者は設備テーブルを更新できます。これは使用開始・終了に必要です。
つまり**権限の面では、使用者が設備名や設備コードも書き換えられます**。

これを画面で抑えるのがフェーズ4-3（ステータス列の読み取り専用化）ですが、
**フォームの読み取り専用はセキュリティ境界ではありません**。API を直接叩けば書けます。

本当に止めたい場合の選択肢は2つです。

1. **列レベルセキュリティ**を設備コード・設備名にも掛ける（確実。ただし管理対象の列が増える）
2. 使用者から設備の Write を外し、**使用開始・終了をフロー経由にする**（確実。ただし操作が数秒遅くなる）

現場で数秒の遅延は致命的なので、**まずは 1 を検討**してください。
パイロット（フェーズ6）の段階では、どちらも入れずに様子を見て構いません。

## 1-9 列レベルセキュリティ

稼働ログの `作業内容` と `終了時コメント` を保護対象にしています。
`Deploy-Security.ps1` がプロファイル「設備-稼働ログ本文」を作りますが、
**誰が読めるかはポータルで追加してください**（自動では追加しません）。

Power Platform 管理センター > 環境 > 設定 > ユーザーとアクセス許可 > 列のセキュリティ プロファイル
> 「設備-稼働ログ本文」 > チーム または ユーザー に「設備-管理者チーム」を追加

プロファイルに入っていない人には、値が `*******` と表示されます。

## 1-10 ビジネスルール（メーカーポータルで作る）

ビジネスルールは Web API から作れないため、ここだけ手作業です。
make.powerapps.com > テーブル > 貸出 > ビジネスルール > 新しいビジネスルール

### ルール1：貸出区分による必須切替

名前：`貸出-区分による必須項目`　スコープ：**エンティティ**

```
条件: 貸出区分 が 社外 と等しい
  → アクション: 貸出先 のビジネス必須 を 必須 に設定
  → アクション: 貸出先部署 のビジネス必須 を 任意 に設定

それ以外の場合:
  → アクション: 貸出先部署 のビジネス必須 を 必須 に設定
  → アクション: 貸出先 のビジネス必須 を 任意 に設定
```

**スコープは必ず「エンティティ」にしてください。** 「すべてのフォーム」にすると、
モデル駆動アプリの画面でしか効かず、キャンバスアプリやフローからの書き込みを止められません。

### ルール2：返却日は貸出日より前にできない

名前：`貸出-返却日の整合性`　スコープ：エンティティ

```
条件: 返却日 に データが含まれる かつ 返却日 が 貸出日 より前
  → アクション: エラーメッセージを表示 「返却日は貸出日より前にできません」（フィールド: 返却日）
```

### ルール3：返却予定日は貸出日以降

名前：`貸出-返却予定日の整合性`　スコープ：エンティティ

```
条件: 返却予定日 が 貸出日 より前
  → アクション: エラーメッセージを表示 「返却予定日は貸出日以降にしてください」（フィールド: 返却予定日）
```

作成したら、各ルールを**アクティブ化**し、ソリューション「設備管理」に追加してください。

## 補足：稼働時間を計算列にしたい場合

`稼働ログ.稼働時間` は通常の整数列として作られ、アプリが終了時に書き込みます。
計算列（終了日時 − 開始日時）にしたい場合は、メーカーポータルで作り直せます。

make.powerapps.com > テーブル > 稼働ログ > 列 > 稼働時間 > 「データ型」を「計算」に変更

```
DIFFINMINUTES(eqm_starttime, eqm_endtime)
```

ただし計算列は**フローの $filter で使えません**。フェーズ5で稼働時間による絞り込みを
する予定があるなら、通常の列のままにしておいてください。
