## 本番環境への移送

展開の前に、開発環境で作ったものを本番へ移します。

```
1. ソリューション「設備管理」を マネージド でエクスポート
2. 本番環境にインポート
3. 接続参照（Dataverse / Office 365 Outlook）をサービスアカウントに割り当て
4. フローをオンにする
5. Deploy-Security.ps1 を本番環境に対して実行（ロールとチームを作る）
6. Import-MasterData.ps1 で本番データを投入
```

**5 と 6 はソリューションに含まれません。** ロールはソリューションに入りますが、
Entra グループチームとの紐付けと、データそのものは移送されません。

本番の環境 URL でスクリプトを流してください。

```powershell
.\Deploy-Security.ps1 -EnvironmentUrl 'https://contoso.crm7.dynamics.com' `
    -UserGroupObjectId '<...>' -AdminGroupObjectId '<...>'
.\Import-MasterData.ps1 -EnvironmentUrl 'https://contoso.crm7.dynamics.com' -All
```

## 7-1 ラベル貼付（使用頻度順）

**この工程が展開の律速です。** 台数が増えると人手と時間が読みにくくなります。

パイロット（6-2）で測った1台あたりの所要時間から見積もってください。

| 台数 | 1台3分として | 
|---|---|
| 100台 | 5時間（1人日） |
| 500台 | 25時間（3〜4人日） |
| 1000台 | 50時間（7人日） |

順番は**使用頻度順**です。よく使う設備から貼れば、早い段階でログが溜まり始めます。
場所順に機械的に回ると、月1回しか使わない設備に時間を使うことになります。

進捗管理は管理者アプリの「ラベル未貼付一覧」（4-4）で行います。
**残り件数を毎日見てください。** 見ないと止まります。

## 7-2 全使用者のマスタ登録

`phase2-initial-data.md` の Microsoft Graph スクリプトで一括取得し、投入します。

登録後、必ず確認すること：

- ビュー「UPN 未設定の使用者」が **0件** であること
- 新入社員・異動者を毎月取り込む運用を 7-7 の手順書に入れること

ここが放置されると、新しく来た人が「アプリが使えない」と言い出します。

## 7-3 Teams へのアプリ埋め込み

現場が Teams を日常的に使っているなら、埋め込むと起動のひと手間が消えます。

```
make.powerapps.com > アプリ > 設備管理 > … > Teams に追加
→ Teams のチャネル > + > Power Apps > 設備管理 を選択
```

**ブラウザのブックマークより到達率が高い**のが利点です。
ただし Teams を開かない職種（工場の現場端末など）には効きません。
その場合は、端末のホーム画面にショートカットを置いてください。

## 7-4 Power BI

Dataverse への直接接続（DirectQuery）ではなく、**インポート**を推奨します。
現場の操作が遅くなるのを避けるためです。

### 取り込むテーブル

`稼働ログ` / `設備` / `場所` / `設備種別` / `使用者` / `貸出`

### 最低限のレポート

| ページ | 内容 |
|---|---|
| 稼働率 | 設備別・場所別の稼働率（下の定義を使う） |
| 使用実績 | 月別・使用者別の稼働時間 |
| 貸出 | 貸出中・延滞の一覧と推移 |
| 品質 | 終了忘れ件数・整合性チェック検出件数の推移 |

最後の「品質」ページを忘れないでください。**仕組みが健康かどうかを見る唯一の場所**です。

## 7-5 稼働可能時間の定義確定

**ここだけは順序を守ってください。6-5 の実データを見てから決めます。**

稼働率の分母をどう定義するかで、出てくる数字がまったく変わります。

| 定義案 | 分母 | 向く場面 |
|---|---|---|
| A. 暦時間 | 24時間 × 日数 | 24時間稼働の設備 |
| B. 就業時間 | 8時間 × 稼働日数 | 一般的な設備 |
| C. 設備ごとに設定 | `設備.稼働可能時間` ÷ 日 | 設備によって運用時間が違う |

雛形は B（480分/日）で入れてあります。

### 決め方

6-5 で取ったヒストグラムを見て、**実際の稼働時間の上限**を確認してください。

- 上限が8時間に張り付いている → B でよい
- 8時間を超えるログが常態 → C にして設備ごとに設定する
- 夜間も動いている → A を検討する

決めたら `設備種別.既定稼働可能時間` と `設備.稼働可能時間` を更新し、
Power BI のメジャーに反映します。

```
稼働率 = SUM(稼働ログ[稼働時間]) / (SUM(設備[稼働可能時間]) * 対象日数)
```

**先に定義を決めてしまうと、実態と合わない数字がひとり歩きします。**
「稼働率30%」という数字が独り歩きして設備を減らす判断に使われる、というのが最悪の結末です。

## 7-6 行レベルセキュリティ

全社展開すると、他部署の稼働ログまで全員に見えている状態が問題になることがあります。

### 現状（パイロットまで）

- 設備・稼働ログ・貸出はすべて **Global** で読める
- 稼働ログの `作業内容` `終了時コメント` だけ列レベルセキュリティで保護（1-9）

### 絞り込む場合の選択肢

| 方法 | 効果 | 手間 |
|---|---|---|
| 事業部（BU）を部署ごとに作り、ロールの範囲を **Local** にする | 自部署の行だけ見える | 大。使用者の BU 割り当てが必要 |
| 列レベルセキュリティを増やす | 特定の列だけ隠せる | 小 |
| ホーム画面の既定表示を自部署に絞る（見せ方の工夫） | 実質的に十分なことが多い | 極小 |

**まず3つ目を検討してください。** 「他部署のログを見られると困る」という要件の多くは、
実際には「普段の画面に出てこなければよい」で足ります。

BU を分けると、設備の貸し借りが部署をまたぐたびに権限の問題が起きます。
本当に監査要件があるのかを確認してから着手してください。
